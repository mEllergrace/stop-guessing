EXECUTIVE VERDICT
-----------------
The repository contains useful assurance primitives and unusually candid internal commentary,
but the application is not presently hardened enough to support its public 21/21 deployed-system
assurance claim.

The repeated failure pattern is:

    a primitive exists and is tested,
    but the installed/runtime surface either does not invoke it,
    invokes it too late,
    bypasses the trusted boundary,
    or is not mechanically included in proof validity.

The present proof gate can establish that a self-authored procedure ran and touched selected
Python modules. It does not establish that every declared CLI, hook, plugin, command, skill, or
daemon surface performed the stated behavior. Several current claims name hooks that are not
registered at all.

This report should be treated as a RELEASE BLOCKER. The honest current status is:

    useful primitives demonstrated;
    deployed assurance and integration not yet proven;
    several security claims invalidated by direct runtime bypasses.

SG-HARD-001 — CRITICAL — Proof validity does not include the claim's declared runtime surface
-----------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-01, 02, 03, 04, 11, 13, 14, 20, 21; potentially all claims with surface entries

Evidence locations:
  - docs/claims.yaml — surface declarations
  - stop_guessing/prove/runner.py — run_one(), check(), _must_touch()
  - stop_guessing/prove/witness.py — module/call witness only
  - .claude-plugin/plugins/stop-guessing/hooks/hooks.json — only PreToolUse and PostToolUse registered
  - stop_guessing/prove/procedures.py — CLAIM-11/13/14 direct library calls

Finding:
runner.check() validates chain state, record reference, passed flag, claim ID, procedure digest,
proof kind, and an execution witness. It never validates docs/claims.yaml:surface.

Concrete current mismatches:
  - CLAIM-11 declares hook:PreCompact; no PreCompact hook is registered. The procedure directly
    builds records and calls rebuild().
  - CLAIM-13 declares hook:Stop; no Stop hook is registered. The procedure directly calls reconcile().
  - CLAIM-14 declares hook:SessionStart; no SessionStart hook is registered. The procedure directly
    calls workbook inspection.
  - Several CLI claims exercise underlying Python functions rather than the packaged console command.
  - Plugin/skill/command claims are satisfied by file/manifest presence rather than invocation.

This is the exact class described by issue #29: a primitive can work while the installed system does
not use it. Issue #29 was closed by adding a non-blocking judge panel; that does not mechanically
close the surface-validation defect.

Minimal reproduction / validation:
Compare each claim's surface list to:
  1. the installed hook manifest;
  2. subprocesses actually launched by its proof;
  3. the proof witness stored in the ledger.
The current proof record has no canonical per-surface witness field to compare.

Required remediation:
Add a controlled surface vocabulary and a fail-closed validator:
  cli:<canonical argv>
  hook:<event + installed entrypoint digest>
  plugin:<installed plugin id/version/root>
  command:<actual command invocation>
  skill:<actual skill load/invocation>
  daemon:<socket peer/process/service identity>

Capture subprocess argv, executable digest, cwd, environment profile, installed root, hook event,
and exit/result. Require every declared surface to be observed by at least one current proof.
Unsupported surface kinds must fail, not be ignored. Invalidate all legacy proof records that lack
the new surface witness.

Required regression/integration tests:
Mutation test: replace a real hook proof with a direct library call and assert the claim becomes
UNPROVEN. Remove a hook from hooks.json and assert every claim naming it fails. Execute the installed
plugin in a clean profile with the repository absent from PYTHONPATH.


SG-HARD-002 — CRITICAL — A claim can remain PROVEN after its proof procedure is deleted
-----------------------------------------------------------------------------------------
Affected claims/surfaces:
  All claims

Evidence locations:
  - stop_guessing/prove/runner.py — check(): proc lookup, source check, kind_ok
  - stop_guessing/cli/cmd_prove.py — cmd_claims_check() display ordering

Finding:
runner.check() sets kind_ok to true when proc is None. A historical passing ledger record may remain
live because no current procedure exists to compare its digest against. The row can therefore be
proven=True while has_procedure=False. The CLI selects the PROVEN label before considering
has_procedure, so the missing procedure may be hidden in normal output.

Minimal reproduction / validation:
Prove one claim, remove its decorated procedure from the registry without changing claims.yaml,
then run claims check. The historical record can still satisfy the row.

Required remediation:
A current procedure must be mandatory:
  proven = chain_ok AND has_procedure AND kind_matches AND live_surface_proof.
Missing procedure is an unconditional invalidation. Add the procedure registry digest to the
release manifest.

Required regression/integration tests:
Delete/rename one procedure after a proof and assert UNPROVEN with a named missing-procedure finding.


SG-HARD-003 — CRITICAL — Proof staleness binds only the decorated procedure, not the implementation under test
----------------------------------------------------------------------------------------------------------------
Affected claims/surfaces:
  All claims

Evidence locations:
  - stop_guessing/prove/registry.py — Procedure.source_digest()
  - stop_guessing/prove/runner.py — comparison to procedure_digest

Finding:
A proof record pins inspect.getsource() of the decorated proof function only. It does not bind:
  - implementation modules called by the procedure;
  - policy and classification YAML;
  - handler indexes;
  - plugin/hook manifests;
  - installer;
  - generated wrapper scripts;
  - packaged wheel or installed runtime;
  - dependencies and interpreter.

Production behavior can change materially while the old proof remains current because the proof
function source did not change.

Minimal reproduction / validation:
Change a policy YAML or an implementation helper used by a proof, leave the proof function untouched, and run claims check.

Required remediation:
Pin a reproducible evidence subject:
  - git tree/commit;
  - wheel digest;
  - installed file manifest and executable digests;
  - rules/policy/config schema digests;
  - interpreter and dependency lock digest;
  - hook/plugin manifests;
  - external fixture/template digests.

A proof is current only for the exact evidence subject it exercised.

Required regression/integration tests:
Mutation matrix: change each implementation, rule, policy, manifest, and wheel subject and require proof invalidation.


SG-HARD-004 — CRITICAL — Truncated proof ledger can still yield full attestation
----------------------------------------------------------------------------------
Affected claims/surfaces:
  All claims, especially CLAIM-20 and CLAIM-21

Evidence locations:
  - stop_guessing/ledger/sink.py — LoadedLog.truncated and load()
  - stop_guessing/prove/runner.py — chain_ok uses only loaded.chain.intact

Finding:
load() preserves an intact prefix and separately reports truncated=True. runner.check() treats only
chain.intact as the release condition. A torn or malformed final proof record can leave every cited
earlier proof live and still produce 21/21 and GOAL MET, even though the sink itself refuses further
writes.

Minimal reproduction / validation:
Append a partial JSON fragment to the proof ledger after all passing proof records, then run claims check and attest.

Required remediation:
Set chain_ok = loaded.chain.intact AND NOT loaded.truncated. Expose chain_truncated in every verdict and derived artifact.

Required regression/integration tests:
Torn tail, malformed middle record, invalid UTF-8, and appended garbage must all fail claims, attestation, CAIQ derivation, page generation, and export.


SG-HARD-005 — CRITICAL — The CI Claims gate accepts every nonzero result
--------------------------------------------------------------------------
Affected claims/surfaces:
  Repository-wide release assurance

Evidence locations:
  - .github/workflows/ci.yml — Claims gate step

Finding:
The workflow captures the exit code from claims check and unconditionally echoes it. It never exits
nonzero for unproven claims, malformed evidence, key mismatch, or command failure. The named release
gate is therefore informational only.

The workflow also has no observable status returned for the audited commit through the connected API.

Minimal reproduction / validation:
Make claims check exit 1 or 2 in a pull request; the step reaches echo and succeeds.

Required remediation:
Define a machine-readable exit contract and enforce it:
  0 = verified;
  1 = finding -> fail;
  2 = cannot verify -> fail protected release jobs, optionally skip only a clearly non-authoritative
      contributor job;
  any other code = command failure -> fail.

Create a protected release workflow running where the key/evidence bundle is available, publish a
signed attestation artifact, and require it for release/tag protection.

Required regression/integration tests:
CI mutation job deliberately causes each exit code and asserts the workflow conclusion.


SG-HARD-006 — CRITICAL — The advertised tier-2 installer cannot start a separate-UID recorder
-----------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-12, LOG-10/IAM-AG-03 mappings, installation assurance

Evidence locations:
  - install.sh — install_recorder(), SERVICE_USER, plist generation
  - stop_guessing/recorder/daemon.py — socket and ledger locations
  - stop_guessing/recorder/client.py — tier inference

Finding:
The installer computes target_uid but never uses it. It writes a LaunchAgent under the logged-in
user's ~/Library/LaunchAgents, which runs as that user. It then chowns the key and ledger to
_stopguessing while runtime and socket parents remain inside the user's profile tree, initially
mode 700. The service account cannot traverse or execute the required files.

Additional architecture failures:
  - the agent user is not placed into a deliberate shared socket group;
  - socket ownership/group is not established for cross-UID access;
  - long-path socket fallback is under the daemon UID's private temp path;
  - the same plist label/path is reused across profiles;
  - the installer only prints launchctl bootstrap rather than executing and verifying it;
  - ProgramArguments resolve /usr/bin/env and python3 from ambient state.

Minimal reproduction / validation:
Run install.sh --isolated on macOS and inspect launchctl process UID, key readability, runtime traversal, and socket connectivity.

Required remediation:
Immediately make --isolated refuse with exit 2. Re-enable only after implementing:
  - a root-installed LaunchDaemon (and systemd unit on Linux);
  - service-owned immutable runtime, key, ledger, and seal directory;
  - explicitly shared socket directory/group;
  - verified peer credentials;
  - per-profile service identity;
  - lifecycle start/stop/upgrade;
  - end-to-end test proving daemon UID differs and the agent cannot read the key or ledger.

Required regression/integration tests:
OS-level separate-UID integration test; chmod/chown/path traversal matrix; multiple profiles; restart/upgrade/uninstall.


SG-HARD-007 — CRITICAL — Tier 1 and the default keyfile do not separate the key from the recorded agent
---------------------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-02 as a system claim, CLAIM-12, chain-keyed+isolated strength

Evidence locations:
  - install.sh — chain.key creation
  - stop_guessing/attest/keys.py — keyfile provider
  - stop_guessing/recorder/client.py — tier 1 definition
  - stop_guessing/ledger/entry.py — strength()

Finding:
A mode-600 keyfile owned by the same user is readable by any code the agent can run under that user.
The default observe posture does not prevent ordinary classified reads, and arbitrary subprocess code
can read it directly. An agent holding the key can rewrite a fully valid HMAC chain; the chain proof
itself demonstrates this control case.

Calling same-UID daemon operation "key separation" or labeling tier >=1 as
chain-keyed+isolated overstates the boundary.

Minimal reproduction / validation:
From an agent-run subprocess, read $CLAUDE_CONFIG_DIR/stop-guessing/chain.key and use it to recompute a replacement ledger.

Required remediation:
Rename strength levels to distinguish format from adversarial custody:
  hmac-keyed-same-authority
  key-custodied-separate-uid
  hardware/remote-custodied

Do not use "isolated" until the agent OS authority cannot obtain the key. Prefer a separate service
identity, hardware-backed key, or remote recorder.

Required regression/integration tests:
Attempt key read through Read, Bash, Python, symlink, hardlink, inherited fd, backup, and service misconfiguration.


SG-HARD-008 — CRITICAL — PostToolUse bypasses cocd and silently loses records under real key separation
---------------------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-01, CLAIM-12, CLAIM-20; derivation and execution-corroboration claims

Evidence locations:
  - stop_guessing/cli/hook_post.py — record_result()
  - stop_guessing/recorder/client.py — append()
  - stop_guessing/recorder/daemon.py — single-writer path

Finding:
hook_post writes directly through ledger.sink.record() using chain_key(). It does not call
recorder.client.append(). Under a true separate-UID design the hook should have neither the key nor
ledger write permission, so the append fails.

The exception is caught inside record_result() and converted to None. main() sees no exception and
returns success without recording a gap. Every PostToolUse execution/result/derivation record can
therefore disappear silently at the exact isolation tier the project says is strongest.

Minimal reproduction / validation:
Run cocd under another UID with hook user denied key/ledger access, execute a permitted write, and inspect the ledger.

Required remediation:
Route all PostToolUse records through the daemon; require a returned append reference; treat refusal/loss as a critical state with an emergency audit path.

Required regression/integration tests:
Same-UID and separate-UID PostToolUse success, daemon refusal, daemon outage, wrong key, broken chain, and permission failure.

SG-HARD-010 — CRITICAL — The recorder authenticates ordering, not event truth
-------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-12, CLAIM-13, event authenticity language

Evidence locations:
  - stop_guessing/recorder/daemon.py — _Handler.op_append()
  - stop_guessing/recorder/client.py — unauthenticated request
  - stop_guessing/ledger/reconcile.py — unused runtime reconciliation

Finding:
Any local process that can connect to the Unix socket may submit arbitrary event content. cocd strips
caller-selected chain fields and assigns sequence/hash, which protects ordering, but it does not
authenticate the actor, hook, tool_use_id, event type, or truth of the event.

There is no peer-credential allowlist, request MAC/capability, dispatch nonce issuance in runtime,
or lifecycle reconciliation. A keyed fabricated event is still fabricated.

Minimal reproduction / validation:
Connect directly to recorder.sock and append an event claiming any actor/action/session.

Required remediation:
Use OS peer credentials and an explicit admission policy. Separate event classes:
  recorder-owned dispatch;
  host-hook result;
  agent-reported corroboration.

Issue nonces/capabilities from recorder-owned state. Reconcile missing, replayed, mismatched, and
fabricated events at batch/session close. State the remaining trust in the host hook honestly.

Required regression/integration tests:
Unauthorized UID/GID, allowed hook process, forged actor, replay, missing result, duplicate result, wrong nonce, and socket theft.

SG-HARD-014 — CRITICAL — Rules, policies, and handler declarations are untrusted mutable inputs
-------------------------------------------------------------------------------------------------

SG-HARD-015 — CRITICAL — Symlink aliasing bypasses PreToolUse classification
------------------------------------------------------------------------------
Affected claims/surfaces:
  Credential/data classification and every read-policy claim

SG-HARD-017 — CRITICAL — Project handler code executes on classified data before policy authorization
-------------------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-08, CLAIM-09, CLAIM-10; delegated handling

Evidence locations:
  - stop_guessing/cli/gate.py — handlers.substitute() before ps.evaluate()

SG-HARD-018 — CRITICAL — Signed-script execution can be bypassed by its paired test
-------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-10 and signed delegation

Evidence locations:
  - stop_guessing/cli/cmd_ops.py — cmd_run() verifies signature before run_test()
  - stop_guessing/delegate.py — run_test() pins post-test digest; run() executes it

Finding:
With --signed, the script signature is verified first. The unsigned paired pytest then runs and can
rewrite the script. run_test() records the rewritten script's digest as the passing tested digest.
run() executes the rewritten unsigned bytes without rechecking the signature.

Minimal reproduction / validation:
Create a signed benign script and a test that rewrites it to a different payload, then returns success.

Required remediation:
Tests must run against immutable snapshots and cannot mutate the executable subject. Verify signature and test result over one content digest, then execute exactly those already-open bytes or a service-owned content-addressed object.

Required regression/integration tests:
Test rewrites script, script rewrites test, symlink swap, rename swap, concurrent replacement, and signature sidecar replacement.


SG-HARD-019 — CRITICAL — Delegation has test/hash/execute TOCTOU races
------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-09 and CLAIM-10

Evidence locations:
  - stop_guessing/delegate.py — run_test(), run(), verify_script()

Finding:
The path is tested, hashed afterward, later hashed again, and then executed by pathname. A concurrent
replacer can make untested bytes inherit the passing digest or replace the file after the last digest
check. Signature verification has the same check-then-open race.

Minimal reproduction / validation:
Coordinate a second process to replace the pathname between test/hash and hash/exec.

Required remediation:
Open/snapshot once, test immutable bytes, bind evidence to content digest, and execute from the same open fd or immutable CAS. Never use a mutable pathname as the security subject.

Required regression/integration tests:
Deterministic barrier-based swaps at every transition.


SG-HARD-020 — CRITICAL — The deployed bar path sends full handler output to model-visible context
---------------------------------------------------------------------------------------------------
Affected claims/surfaces:
  CLAIM-10

Evidence locations:
  - stop_guessing/prove/procedures.py — proof calls emit_for_model(handle/summary)
  - stop_guessing/cli/gate.py — _substituted() includes sub.output in decision reason
  - stop_guessing/delegate.py — default test only requires string output
  - Official Claude hook docs — deny reason is shown to Claude

Finding:
The proof demonstrates an unused helper. The deployed path does not call emit_for_model(); it embeds
sub.output in full in the hook decision reason. A handler that returns the file contents can therefore
place protected bytes in model-visible context while the record says delegated handling occurred.

SG-HARD-051 — HIGH — Mixed full and flat records make deployed sufficiency structurally unattainable
